# txtx 项目流程梳理

本文记录当前代码库里“真实在运行”的主流程，方便后续继续收敛架构和补功能。

## 1. 项目定位

`txtx` 是一个本地单机小说下载工具。

用户流程目标很简单：

1. 配好本地保存目录、站点和规则
2. 从首页发起扫描、单本下载或批量导入
3. 在任务中心确认书单、观察进度、处理失败项
4. 把结果保存到本地书架，并在历史记录里追溯

## 2. 技术结构

### 前端

- `src/` 下是 React + Vite 前端
- 路由入口在 `src/router.tsx`
- 全局布局在 `src/layouts/RootLayout.tsx`
- 平台适配在 `src/platform/`
- API 封装在 `src/lib/api/`
- 状态主要分为：
  - `configStore` / `aiStore`：配置类状态
  - `taskStore`：当前主任务体系
  - `downloadStore`：旧下载兼容流，仍有少量展示和接口依赖
  - `schedulerStore` / `schedulerRunner`：每日批量任务调度

### 后端与桌面端

- `src-tauri/` 下是 Rust + Tauri
- `txtx-server` 是 Web 开发模式使用的 Axum HTTP 服务
- `txtx-app` 是 Tauri 桌面应用入口，需要 `tauri-build` feature
- 下载、扫描、历史、任务持久化、本地文件能力都在 Rust 侧完成
- 默认 HTTP 服务端口是 `3721`，Vite 前端端口是 `1420`

## 3. 页面职责

### 首次运行

- `RootLayout` 启动时调用 `apiCheckFirstRun`
- 如果是首次运行，展示 `SetupWizard`
- 用户完成目录选择后，写入配置并进入正常页面

### 首页 `DownloadPage`

当前首页已经收敛成“任务发起台”。

主要职责：

- 选择扫描日期范围
- 选择扫描站点
- 发起扫描任务
- 发起单本下载任务
- 批量导入 URL 并创建任务
- 在发起前做站点健康预检
- 当已有任务在运行时，引导用户去任务中心查看和操作

首页不再建议承载完整下载状态机。

### 任务中心 `TaskManagerPage`

这是当前推荐的主流程页面。

主要职责：

- 展示任务列表
- 搜索、筛选、排序和汇总任务
- 查看扫描中、预览待确认、下载中、已暂停、已完成、已失败任务
- 在扫描完成后展示候选书单
- 保存扫描预览的选择、站点筛选和排序草稿
- 确认下载选中项
- 查看日志与失败报告
- 重试、暂停、取消、删除任务

### 规则管理 `RulesPage`

负责维护站点规则，使用向导编辑：

- 站点域名
- 列表页规则
- 章节页规则
- 内容 XPath
- 编码覆盖
- 广告清理预览
- AI 辅助 XPath 抽取

### 其他页面

- `SettingsPage`：通用配置、路径、网络、并发、电子书、AI、后处理
- `FilterPage`：过滤、广告清理、黑名单、白名单
- `HistoryPage`：下载历史分页、筛选、排序、统计、重新下载
- `HealthPage`：站点健康检查
- `ConverterPage`：文本转换、拆分、合并
- `BookshelfPage`：本地书架浏览、打开、删除和质量检查

## 4. 当前主流程

### A. 扫描下载流程

1. 用户在首页选择时间范围和站点
2. 首页调用 `taskStore.createScanTask`
3. 前端跳转到任务中心
4. Rust 后端开始扫描，持续发出 `task_event` 或通过 `/api/tasks` 被轮询到
5. 扫描完成后任务进入预览待确认状态
6. 用户在任务详情里筛选、排序并选择要下载的书
7. 前端保存预览草稿，并调用 `confirm_task_download` / `/api/tasks/{id}/confirm`
8. 后端继续执行下载
9. 下载完成后任务状态变成完成，并写入历史与本地文件

### B. 单本下载流程

1. 用户在首页输入 URL
2. 前端创建 `single_download` 任务
3. 用户在任务中心查看进度和日志
4. 任务完成或失败后可以重试

### C. 批量导入流程

1. 用户在首页导入多个 URL
2. 前端清洗、去重并逐条创建单本下载任务
3. 任务创建失败会按 URL 汇总提示
4. 用户去任务中心统一查看结果

### D. 历史重新下载流程

1. 用户在历史页筛选或定位旧记录
2. 点击重新下载后创建新任务
3. 前端跳转到任务中心
4. 后续仍走任务体系

## 5. 前后端数据流

### 配置流

- 前端通过 `configStore` 调 `apiLoadConfig` / `apiSaveConfig`
- Rust 侧通过 SQLite 配置表持久化
- 首次运行目录由 `SetupWizard` 写入配置

### 任务流

- 前端通过 `taskStore` 创建任务
- Rust 侧生成 `TaskRecord`
- 扫描 / 下载过程中不断发出任务事件
- 桌面模式监听 Tauri `task_event`
- Web 开发模式轮询 `/api/tasks`
- 前端合并任务快照并更新列表与详情
- 任务、预览草稿、失败信息和完成元数据落到 SQLite

### 历史与书架流

- 下载完成后 Rust 写入历史记录和本地文件
- 历史页通过 `/api/history/page` 分页查询，通过 `/api/history/stats` 获取统计
- 书架页通过 `/api/books` 读取本地目录文件，并提供打开、删除、导出检查结果等操作

### 旧下载流

旧流仍然存在：

- `downloadStore`
- `downloadEventHandler`
- `/api/scan`
- `/api/download*`
- `/api/queue`
- `/api/stop`

这套流还没有彻底移除，但新入口默认优先走任务体系。后续新增功能应避免扩大旧流职责。

## 6. 已完成的收敛

- 首页单本下载改为创建任务
- 首页批量导入改为创建任务
- 首页扫描入口改为创建扫描任务并跳转任务中心
- 单本任务保存 `source_url`，重试可闭环
- 任务中心承接扫描预览与确认下载
- 命令面板中的扫描入口已改为创建任务
- 历史页中的重新下载已改为创建任务并跳转任务中心
- 首页未完成队列提示已改为引导用户前往任务中心
- 旧结果页中的“再次扫描”已改为返回任务发起台/任务中心
- 任务列表已支持搜索、状态筛选、类型筛选、排序和摘要
- 历史页已使用后端分页、站点选项和统计，减少大数据量前端压力
- 任务快照与预览草稿可持久化，桌面端重启后可继续确认下载

## 7. 质量与性能关注点

### 测试

- 任务创建、任务同步、预览草稿、重试和错误提示需要优先补测试
- 列表型页面要覆盖搜索、筛选、排序、分页、空状态和错误态
- 平台差异要覆盖 Web/Tauri 能力判断和 fallback
- 测试不要依赖真实网络、真实小说站点或本机目录

### 性能

- 历史、任务、扫描预览、书架都可能面对大量数据
- 前端筛选排序应避免修改输入数组，摘要统计尽量单次遍历完成
- 历史分页和统计应继续放在后端，不要回退为前端全量分页
- 高频任务事件需要合并快照、保持对象复用，避免无意义重渲染
- 大型依赖应确认加载边界，优先让单页功能进入独立 chunk

## 8. 仍需继续完善的点

### 高优先级

- 继续减少首页对 `downloadStore` 的依赖
- 把旧扫描预览组件改造成任务页可复用组件，或逐步退场
- 统一“暂停/恢复/停止”在首页与任务页的行为语义

### 中优先级

- 为任务流补更完整的交互验证
- 给任务创建失败补更明确的用户提示
- 梳理任务列表与首页状态提示之间的关系

### 低优先级

- 清理已不再走主路径的旧文案
- 统一“下载控制台 / 任务中心 / 扫描预览”等命名

## 9. 当前建议

后续开发默认遵循下面这条原则：

“首页负责发起，任务中心负责执行与查看，Rust 后端负责真实状态与持久化。”

只要继续沿这个方向推进，项目流程会越来越清晰，状态分裂也会逐步消失。
